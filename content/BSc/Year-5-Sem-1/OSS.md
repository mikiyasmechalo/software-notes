# CH 1: Introduction to OSS
**Software Engineering**  is an engineering based approach to design, develop, test and maintain a piece of software.
- its goal is to develop software applications for improving quality, budget and time efficiency.
- ensures consistency, correctness, is on budget & on time and within the requirements.

- Software Engineering paradigms define the fundamental principles, methodologies and practices used to develop high-quality software systems.
- e.g. Procedural, OOP, Functional, Agile, DevOps, SaaS, etc..
- The chosen paradigm significantly influences how developers design, write and maintain software.
- It affects code readability, maintainability, and the overall structure.
- Factors to choose the right paradigm
	- Problem domain
	- Complexity
	- Performance
	- Developer Familiarity

**What is OSS?** 
OSS refers to software that is released with a license that allows anyone to view, modify and distribute the source code.
It promotes collaboration and transparency, enabling developers worldwide to contribute to projects.

OSS represents a new way of dealing with intellectual property.
- **Transparency**: Anyone can inspect the code.
- **Collaboration**: Community-driven development.
- **Licensing**: Governed by open-source licenses (MIT, GPL, GNU)

At its core opensource is **an Idea**, a concept that evolves around *access*.
- with access to the source code, one can customize the software for his/her use case, find bugs and fix them.
- and even share their "version" with others.

Open source powers the internet.
- 60% of all websites run on Apache and Nginx.

### Open Source Paradigm
- refers to an approach to S.D where the source code is open and collaboration is encouraged.
- Technically, OSS is defined in terms of distribution license not development methods.

- users must have freedom (characteristics)
	- to run the program/software for any purpose
	- to study how the program works and modify it to suit their needs
	- to redistribute copies freely
	- to improve the program and release their improvements to the public.

**Characteristics of Open Source** 
- *Transparency* - the open nature allows for greater scrutiny, which can lead to improved security and quality through peer review.
- *Licensing* - OSS is released under licenses that comply with the OSS definition, e.g. GNU, GPL
- *No Vendor Lock-in* - users are not tied to a specific vendor, allowing for flexibility in usage and support.
- *Continuous Improvement* - The collaborative nature of open source encourages ongoing enhancements and updates from the community.

# CH 2: Economics and Business Models of Open Source
## Closed source vs. Proprietary Software
- often interchangeably used but different.

**Closed Source** - source code isn't available to the public.
- users can only access the compiled version, usually in the form of executables.
- no ability to view or modify the underlying source code.
- *licensing* - may be free to use
- *in house* - a software for internal use, not sold or licensed to others.

**Proprietary** - owned by an individual or company and its usage is restricted through licenses.
- 'proprietary' - signifies that the *rights*, including distribution, modification and use are restricted and protected by *copyright* or other legal mechanisms.
- *licensing* - often requires a paid license, that comes with restrictions on usage, sharing and modification.
	- users must typically agree to these terms before using the software.
	- e.g. commercial software (MS office, Adobe CC), subscription services (Salesforce)

- most proprietary software are closed source but not all closed source is proprietary.
- can proprietary software can also be an opensource? YES.
	- **dual licensing** - some companies release their software with both proprietary and opensource licenses.
		- this enables monetization, often through **Enterprise features** or just the **right to use it commercially** without copyleft, sold under the proprietary license.
		-  e.g. MySQL, MongoDB, QT, Redis

	- **Source available** - access to source code but usage is still restricted by a license.
		- allows viewing and modifying for personal/ evaluation purpose, but may not allow redistribution & modification for commercial purposes.
		- e.g. Oracle JDK, GitLab, Xamarin

	- **Shared Source initiative** - a licensing model introduced by Microsoft that allows users to access the source code of certain Microsoft products under specific conditions.
		- allows for greater transparency and collaboration but is still proprietary.
		- e.g. `.Net` framework, Windows Internals

## Free vs Open Source
- closely related concepts but differ in philosophy and focus.

**Free** 
- emphasizes 'user freedom' and 'control', and not 'price'.
- supported by the **FSF** & **Richard Stallman**.
- it is a moral and ethical imperative.
- Four essential freedoms: **use/run**, **study**, **modify/improve** and **share/redistribute**.
- The **GPL** license is designed to protect these freedoms forever. ("copyleft"-ensures freedoms are preserved forever across all derivative works)

**Open Source** 
- emphasizes practical *collaboration* and *development* to create better software.
- focuses on the benefit of opensource for building *quality* software.
- has its code publicly under a license that respects:
	- free distribution
	- modification of source code
	- ability to distribute modified versions

**Free vs. Open Source** 
*Philosophy* 
- 'Free' software advocated for user rights
- 'Open source' focuses on development advantages.

*Source Code* 
- 'Free'  software doesn't necessarily require open source code.

*Key Advantage for users* 
- 'Free' - freedom to use, modify and distribute
- 'Open source' - Access to source code for better security, customization etc..

## Free and Open Source Software (FOSS)
- Software that respects user freedom and is open source.
- OSS promotes sharing, collaboration, community engagement, transparency, and the ability to customize software for individual or organizational needs.
- e.g. Linux, Apache HTTP server, Firefox.

### Open Source vs Source Available
**Open Source** 
- grants broader permissions.
- open-source projects promote more collaborations and openness, w/c can lead to innovation and bug fixes.
- there are well-defined licenses like MIT and Apache 2.0

**Source-available** 
- more restrictive
- there may be limitations on how we can use or modify the source code. Like:
	- 'field of use': restrictions on usage for specific purposes, like 'only personal'...
	- 'modification and distribution':  might not be allowed to modify or redistribute.

**Key Differences** 
*Freedoms* - open source grants freedom to use, modify, and distribute.
*Licenses* - OS uses specific licenses that uphold these freedoms.
*Development* - OS encourages community and development.
*OSS is like a public park* - everyone can come in, play and help improve the facilities.
*Source-available is like a museum with a glass window* - you can see but can't touch unless given permission.

## Economic Paradox in Open Source
**The $0 price tag** 
In traditional microeconomics software is **non-rivalrous** (one person's use doesn't prevent another's) but it is **excludable** (usage can be prevents via licensing)
- This excludability is the basis of traditional software monetization.

Opensource deliberately removes excludability.
- This appears to violate basic economic principles of investment and return.
- But this paradox only if we assume the value of a software is solely and exclusively contained within the **bits** of the **executable** and its **direct license fee**($0).

**The Resolution** - The value of a software isn't just about the code, it is in the **ecosystem**, **support**, **readability**, **brand** and **market position** it creates.
- OSS business models are about creating value through the code and capturing value elsewhere.

### Value Creation vs. Value Capture of OSS

**Value Creation** - how OSS generates value for the world 
- Collaborative environment - all improving code, finding bugs, adding features
- Rapid innovation - faster iteration
- Standardization - becoming a do facto standard (e.g. Linux for servers, Kubernetes)
- Massive adoption - low barrier to entry, network effects and rich ecosystems.

**Value capture** (monetization) - capturing a part of the generated value as revenue.
- Selling scarcity - More features (open core), Legal certainty (Dual license)
- Selling convenience - hosting, management and support (SaaS, support services)
- Selling influence - priority access to roadmap, dedicated resources.

## Economics of Open Source
1. **Cost Structure** 
	- Free to use - no cost to download, use and modify.
	- Support costs - organizations often incur costs related to support, maintenance and training

2. **Business Models**  (more detail later)
	- *Freemium Model* - offering basic features for free while charging for advanced features, support and services. e.g. Red Hat, Trello
	- *Dual licensing*  - software offered under both open source and proprietary license, this allows developers to monetize the software in specific contexts. e.g. MySQL
	- *Consulting and Services* - providing consulting, implementation, and customization services for open source software.

3. **Value Creation** 
	- *Community Contribution* - leads to rapid innovation and improvement without the cost.
	- *Network Effects* - as more people use and contribute to a project, its robustness and feature set improve, attracting even more users.

4. **Market Dynamics** 
	- *Competition with Proprietary Software* - leading to lower prices and better quality in the market.
	- *Vendor Lock-In* - OSS reduces vendor lock-in. 

5. **Investment and Funding** 
	- *Crowdfunding and Donations* 
	- *Corporate Sponsorships* - large companies often sponsor open source projects or contribute to their development to align with their business interests, ensuring the sustainability of key tools they rely on.

6. **Economic Impact** 
	- *Job creation* - in development, support and consultancy
	- *Boosting Innovation* - by allowing developers to build upon existing projects, leading to new applications and technologies that can drive economic growth.

7. **Challenges and Risks** 
	- *Sustainability* - funding and long-term sustainability is not guaranteed in OSS, w/c can affect its viability and ecosystem as a whole.
	- *Quality Assurance*  - The varying levels of quality in open source projects can pose risks for organizations that rely on them, potentially leading to increased costs for support and troubleshooting.

### OSS Business Models

Five common ways companies monetize open-source software:

1. **Freemium** - free base product, paid for advanced features/support.
	 - e.g. Atlassian (Trello, Slack)
2. **Dual Licensing** - free under OSS license, paid under proprietary license.
	 - e.g. MySQL (GPL vs. commercial)
3. **Subscription** - recurring fee for access, updates, and support.
	 - e.g. Red Hat Enterprise Linux
4. **Consulting & Services** - revenue from expertise, not the software.
	 - e.g. Canonical (Ubuntu)
5. **Support & Maintenance** - paid enterprise-grade support and training.
	 - e.g. SUSE
6. **Crowdfunding & Donations** - funding from users/orgs that benefit from the software.
	 - e.g. GIMP, Blender
7. **Sponsorship & Grants** - financial support in exchange for influence or sustainability.
	 - e.g. Google, Microsoft sponsoring OSS initiatives
8. **Open Core** - OSS core, proprietary add-ons for premium features.
	 - e.g. GitLab (free core + commercial editions)
9. **Marketplace** - third parties sell extensions/plugins on top of the OSS core.
	 - e.g. WordPress themes & plugins

> **Summary:** Since the code itself is free, OSS businesses monetize around it - through premium features, licensing flexibility, subscriptions, paid expertise/support, and community or ecosystem funding.

# CH 3 - Open Source Software Criteria and Comparison
The term "**Open Source**" carried specific implications that go beyond more access to source code.
The "**Open Source Initiative (OSI)**" has established a set of criteria known as the **Open Source Definition** to ensure that software labeled as "Open Source" meets certain criteria.

**Open Source Initiative** 
- OSI is a non-profit organization that promote and protects open source software by advocating for the open source model and its benefits.
- OSI is best known for maintaining the Open source definition (OSD), w/c outlines the criteria that software must meet to be considered open source.
- OSI also reviews and approves open source licenses, ensuring they comply with the definition.

Open Source Software Criteria
### The Open Source Definition (OSD)
Open Source Software Criteria:
1. **Free Redistribution** - the license must not restrict any party from selling or giving away the software, and must not require a royalty or fee for such sale.
2. **Source Code** - the program must include source code and allow distribution in both source and compiled form; the source code must be the preferred form for modification, and deliberately obfuscated source code is not allowed.
3. **Derived Works** - the license must permit modifications and derived works, and allow them to be distributed under the same terms as the original.
4. **Integrity of the Author's Source Code** - the license may restrict distribution of modified source code only if it allows "patch files" alongside the source code, so unofficial changes remain distinguishable from the original.
5. **No Discrimination Against Persons or Groups** - the license must not discriminate against any person or group.
6. **No Discrimination Against Fields of Endeavor** - the license must not restrict anyone from using the program in a specific field, including commercial or business use.
7. **Distribution of License** - the rights associated with the program must apply to all to whom it is redistributed, without needing an additional license.
8. **License Must Not Be Specific to a Product** - the rights attached to the program must not depend on it being part of a specific software distribution; if extracted, the same rights apply.
9. **License Must Not Restrict Other Software** - the license must not place restrictions on other software distributed alongside it (e.g., cannot require other programs on the same medium to also be open source).
10. **License Must Be Technology-Neutral** - no provision may be based on any individual technology or style of interface.

These criteria ensure that open-source software is transparent, collaborative, and can be freely used, modified, and shared by anyone for any purpose.

### Key Criteria for Evaluating Open Source Software
- **Open Source License** - distributed under an approved OSS license (MIT, GPL, Apache, etc.), ensuring rights to use, modify, and distribute.
- **Availability** - source code publicly accessible for viewing, modification, and auditing.
- **Freedom to Modify** - users can modify the software and create derivative works.
- **Sharing / Redistribution** - both original and modified versions can be redistributed, promoting collaboration.
- **Comprehensive Documentation** - thorough docs covering installation, usage, and contribution guidelines.
- **Code Quality** - follows best practices for coding and testing, ensuring reliability and performance.
- **Regular Updates** - active maintenance with regular updates and bug fixes indicates a healthy project.
- **Security Audits** - processes in place for identifying and resolving vulnerabilities; benefits from collective scrutiny with effective management.
- **Compatibility and Interoperability** - compatible with other systems and tools for easy integration.
- **Support Channels** - forums, chat rooms, or documentation to enhance user experience and resolve issues.


### Criteria to Choose Open Source Software
1. **Features** - Does the software offer the functionalities you need?
2. **Scalability** - Will it handle your project's size and potential growth?
3. **Security** - How secure is the software? Crucial for projects dealing with sensitive data.
4. **Active Development** - Is it actively maintained by a healthy developer community? Regular updates and bug fixes are essential for long-term use.
5. **Community Support** - Is there an active user community where you can find help and answers?
6. **Documentation** - Does it have clear, comprehensive documentation that's easy to understand?
7. **Team Skills** - Does your team have the necessary skills to use and maintain the software?
8. **License Terms** - Review the license to understand its terms and conditions; some OSS licenses have restrictions on use or modification.
9. **Popularity** - While not always the best indicator, popular OSS often has a larger community and more resources available.

### Open Source Standardization
The process of establishing and promoting standards for open source software projects.
- These standards ensure *compatibility*, *interoperability*, and *quality* across different implementations, enabling a cohesive development environment.

Open Source Standardization combines these ideas by ensuring that standards are:
- Developed in the open (transparent process).
- Implemented through open source reference code (not just documents).
- Accessible to all (free from restrictive IP or paywalls).

**Importance of Open Source Standardization** 
- **Interoperability** - Enables different systems and applications to work together, enhancing user experience.
- **Quality Assurance** - Establishes benchmarks for software performance, security, and usability.
- **Community Collaboration** - Fosters collaboration among developers, reducing redundancy and promoting shared solutions.
- **Reduced Vendor Lock-in** - Allows organizations to switch between software solutions without losing functionality, enhancing flexibility.

#### Principles of Open Source Standardization
1. **Openness** 
	 - *Transparency* - standards developed openly with public review and input
	 - *Inclusivity* - all stakeholders (end-users, developers, organizations) encouraged to participate

2. **Consensus** 
	- *Broad Agreement* - standards reflect consensus among a diverse group of participants
	- *Trust Building* - consensus-driven processes foster trust and buy-in from the community

3. **Flexibility** 
	- *Adaptability* - standards accommodate new technologies and evolving requirements
	- *Support for Innovation* - flexibility allows varied implementations that drive innovation

4. **Documentation** 
	- *Comprehensive Guides* - clear, thorough docs essential for understanding and implementing standards
	- *Consistency* - well-documented standards promote uniform application across projects

#### Processes for Open Source Standardization

**Development of Standards**
- **Proposal Stage** - community members propose ideas for new standards; proposals are discussed and refined based on community feedback.
- **Drafting Stage** - a working group or committee drafts the proposed standard, incorporating stakeholder feedback.
- **Review Stage** - the draft undergoes public review, allowing for additional comments and revisions; community input helps identify potential issues.
- **Approval Stage** - final approval is sought from relevant governing bodies or the community to ratify the standard.

**Implementation**
- **Pilot Projects** - early implementations tested in pilot projects to identify issues and gather feedback; adjustments made based on results.
- **Widespread Adoption** - once refined, the standard is promoted for wider adoption across the community and organizations.

#### Challenges in Open Source Standardization
- **Fragmentation** - multiple competing standards complicate solution choice for users and hinder a unified development approach.
- **Lack of Resources** - limited funding/resources can hinder standardization and slow progress in developing and maintaining standards.
- **Resistance to Change** - organizations may resist new standards due to established practices; change management is essential to encourage adoption.
- **Keeping Up with Technology** - rapid technological advancements can outpace standardization, leading to outdated standards; continuous monitoring of trends is needed.

- **Linux Foundation** - promotes Linux growth and supports diverse OSS projects; hosts events, provides training, manages collaborative projects.
- **Eclipse Foundation** - focuses on OSS development tools/frameworks (e.g., Eclipse IDE); fosters a developer community.
- **Free Software Foundation (FSF)** - advocates for free software and ethical software use; promotes the GNU Project and software freedom campaigns.

- **Mozilla Foundation** - ensures the internet remains a global public resource, open and accessible; advocates for user privacy, security, and open-source technologies.
